## Mitigation

The `ToastEnabled=0` attempt has been removed from the GUI runner. In runs `40675661733` and `40676042015`, creating the `HKCU\Software\Microsoft\Windows\CurrentVersion\PushNotifications` key failed with `Unauthorized operation`; those runs did not record the runner token or registry ACL, so the exact permission cause is unproven. More fundamentally, Microsoft's [ADMX_WPN policy documentation](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-admx-wpn) says that disabling application toast notifications does not affect Windows system features. It therefore was not a valid control for the observed Notification Center surface.

The separate workflow `.github/workflows/gui-runner-desktop-diagnostics.yml` records runner identity, group membership, OS version, and ACLs for the user toast and taskbar policy keys. It is manually dispatchable and runs without project GUI tests when its own workflow file changes in a pull request. It invokes Win+N through the Windows keyboard input API and saves desktop screenshots plus native shell-window snapshots before and after temporarily setting `DisableNotificationCenter=1`. It restores and verifies the exact original registry value in a `finally` path. It does not reboot the host or retain a policy change. Microsoft's [taskbar policy documentation](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-admx-taskbar) identifies `HKCU\Software\Policies\Microsoft\Windows\Explorer\DisableNotificationCenter` as the `Remove Notifications and Action Center` policy and says a reboot is required for it to take effect. A before-reboot result therefore establishes only whether this hosted session responds immediately; it cannot establish effect after reboot.

The first diagnostic [run `40679420384`](https://github.com/tetsuji16/microProject/actions/runs/40679420384) found the PushNotifications key already existed, owned by `NT AUTHORITY\SYSTEM`; its inherited ACL grants full control to the runner's local-account group and `BUILTIN\Administrators`, with no deny ACE. The token was `runneradmin` (SID ending in `-500`), a member of Administrators with a high integrity level. The stage-separated diagnostic [run `40679631765`](https://github.com/tetsuji16/microProject/actions/runs/40679631765) showed that the `PowerShell New-Item -Force` operation on this existing key returns `Unauthorized operation`; direct `.NET RegistryKey.SetValue` on the same `ToastEnabled` DWORD succeeds and is restored to its original absent state. Thus the failure was not a denied value-write ACL; the PowerShell registry provider's `New-Item` operation was rejected even though direct value write succeeded. The candidate policy key was owned by Administrators; PowerShell provider write/readback of `DisableNotificationCenter=1` succeeded, and the absent original value was removed. The first physical-policy [run `40680119431`](https://github.com/tetsuji16/microProject/actions/runs/40680119431) saved the UI before and after the setting, but its state detector incorrectly reported `notificationCenterVisible=False` even when the screenshot and foreground-window snapshot showed the panel open. Its apparent after-policy closure was just the second Win+N toggle, so that run is invalid as policy-effect evidence. The detector now uses the foreground ShellExperienceHost window directly; repeat diagnostic is pending.
