# podx 0.1 container specification

`podx` is an open, interoperable project-file container. This document and the
associated schema are MIT licensed. A conforming implementation must not need
microProject classes or Java serialization.

The 0.x line is intentionally evolvable. New optional ZIP entries and optional
JSON fields may be added without changing legacy `.pod`; a podx reader must
ignore an extension it does not implement and must reject only an unsupported
required major container version.

## Container

A `.podx` file is a ZIP archive encoded with UTF-8 entry names. It contains
exactly one `manifest.json` and one `project.xml`. Unknown entries are optional
extensions and readers must preserve them when they support round-trip editing;
otherwise they must report that they cannot preserve extensions before saving.

`project.xml` is a UTF-8 MSPDI XML snapshot. It carries the interoperable
project, calendar, task hierarchy, dependency, resource, assignment, work,
cost, progress and baseline data available in MSPDI. Version 0.1 deliberately
does not claim lossless representation for vendor-only MSPDI extensions.

When CCPM is configured, microProject writes an optional `ccpm.json` extension
with `schemaVersion: 1`, its enabled state, buffer fraction and resource-leveling
policy. After applying a CCPM plan it also stores an immutable schedule baseline
for project and feeding-buffer consumption; a later analysis recalculates the
remaining amount and warning state from that baseline. Readers that do not
implement CCPM may ignore this entry; readers that do implement it must preserve
these settings on a no-op round-trip.

Legacy `.pod` files are never extended with CCPM state. microProject keeps a
normal project as `.pod`, but changes a requested `.pod` target to `.podx`
when CCPM is enabled so that the setting is not silently lost.

## Manifest

The required manifest fields are:

```json
{
  "format": "podx",
  "version": "0.1",
  "projectEntry": "project.xml",
  "projectSha256": "lowercase SHA-256 of the uncompressed project.xml bytes",
  "documentId": "stable UUID shared by the snapshot and operation log",
  "projectUniqueId": 123
}
```

`documentId` and `projectUniqueId` are optional for standalone interchange and
are emitted by the collaboration writer. Before an external operation-log
merge, `documentId` is required and must equal the operation log's document ID;
`projectUniqueId` is informational because an MSPDI reload may allocate a new
in-memory numeric project ID.

Readers must reject a missing required entry, an unsupported major version, or
a checksum mismatch. They must also reject duplicate required entries or JSON
fields, malformed CCPM data, unsafe extension paths, and archives above their
documented limits. microProject 0.1 limits an individual uncompressed entry to
64 MiB, the complete uncompressed archive to 128 MiB, and the archive to 128
entries. Writers must use a temporary file and replace the target only after the
complete archive is written.

## Compatibility and collaboration

Version 0.1 is a snapshot interchange level. It carries a validated
`changes/operations.json` extension and applies replay-safe task create,
update, delete, move, dependency, and assignment operations after loading the
snapshot. The reference implementation generates those operations by comparing
each podx save.
The companion `changes/task-identities.json` entry maps legacy POD task unique
IDs (including negative/generated IDs) to the positive MSPDI UIDs in
`project.xml`; readers apply this map before replaying operations.
When a later shared-folder save sees the same document ID, it deterministically
unions its task operations with the synchronized operation log, applies newly
merged non-local operations to the in-memory snapshot, and only then replaces
the container; independent task edits are therefore retained immediately.
Concurrent edits
to the same entity resolve by deterministic operation order and should be
protected with task leases. The current microProject collaboration sidecar is
supported for `.podx` files.

For OneDrive shared folders, keep the `.podx` file and its collaboration
sidecar together. See [the shared-folder protocol](onedrive-collaboration.md)
for the current safe behavior and the limits of snapshot-level collaboration.

The current operation contract is documented in
[operation-log-v0.1.md](operation-log-v0.1.md). Semantic merge rules and
automatic conflict presentation and Graph-backed multi-writer coordination
remain future work; deterministic operation-log merging is available for the
supported operation kinds. The optional `appliedOperationIds` field records
the causal operation generation already reflected in `project.xml`, allowing
readers to reject stale or fabricated snapshot state before replay.
