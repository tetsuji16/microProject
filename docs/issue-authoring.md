# issue の書き方と整理のルール

この文書は、issue を書く人と整理する人のためのルールです。issue を実装する側の手順は [`issue-execution.md`](issue-execution.md) にあります。

目標は、**この会話や過去の経緯を知らない実装者が、issue の本文だけを読んで作業を終えられること**です。設計の判断は issue を書く側が済ませ、実装者には判断を残しません。

## 1. 1 つの issue の大きさ

- 1 つの issue は 1 つの PR で終わる大きさにする。目安は、変更するファイルが 10 個以下、レビューする差分が 400 行以下。
- それより大きい作業は、親 issue（ラベル `tracking`）と子 issue に分ける。親にはチェックリストと進める順番だけを書き、作業手順は子に書く。
- 互いに独立した小さな修正をまとめるときは、項目に番号を付け、「項目ごとにコミットを分ける」と書く。
- 設計がまだ決まっていない作業は、実装の issue にしない。先に「調査して方針をコメントする」issue にし、完了条件を「方針がコメントされている」にする。

## 2. 本文の構成

次の見出しを、この順番で使う。テンプレートは `.github/ISSUE_TEMPLATE/` にある。

| 見出し | 書くこと |
|---|---|
| `## 概要` | 何が問題で、利用者や開発者が何に困るか。3〜6 行。原因が分かっていれば書く。 |
| `## 作業手順` | 番号付きの手順。各手順に、対象のファイルとシンボル名を書く。 |
| `## 検証` | 実行するコマンドを、そのまま貼り付けて実行できる形で書く。 |
| `## 完了条件` | チェックボックス。1 行が 1 つの確認で、コマンドの結果かテストで判定できること。 |
| `## 範囲外` | やらないこと。関連する issue があれば番号を書く。 |

すでに一部を実装してある場合は、`## 概要` の次に `## 骨格` を置き、ブランチ名、コミット、済んでいる内容を書く。見出しを `## 残っている作業` に変えて、残りだけを手順にする。

### 書き方の規則

- **場所はパスとシンボル名で示す。** 行番号は補助として書いてよいが、基準にしたコミットを 1 か所に書く（例：「行番号は master `4a2631505` 時点」）。パスが長いときは、探すコマンド（`rg --files -g Foo.java modules`）を書く。
- **手順は「何を、どう変えるか」まで書く。**「適切に処理する」「必要に応じて直す」は書かない。選択肢が残る場合は、どちらを選ぶかの基準を書き、選んだ理由を PR に書かせる。
- **完了条件は観測できる結果で書く。**「正しく動く」ではなく、「`X` を渡すと `IOException` になる（テストあり）」「`rg -n "System\.exit" modules/microproject_core/src/main` が 0 件」のように書く。
- **変えてはいけないものを書く。** ファイル形式（特に POD のバイト列）、スケジュール計算の結果、必須チェックの名前など、その作業で壊しやすいものを完了条件に入れる。
- **所有者の判断が必要なことは、実装させない。** 削除や移行、費用や公開範囲に関わることは、「調査結果と提案をコメントする。判断は所有者が行う」と書く。
- **未確認のことは、未確認と書く。**「原因の候補だが、関係は確かめていない」のように、事実と推測を分ける。
- Microsoft Project との互換に関わる issue は、`msp-compatibility.md` のテンプレートを使い、根拠にした Microsoft の公開文書を書く（[`agent-workflows.md`](agent-workflows.md) の「Microsoft compatibility decisions」）。
- 1 つの文には 1 つのことだけを書く。社内だけの略語や、会話の中で付けた呼び名を使わない。

### 検証の欄に書くコマンド

変更の種類ごとに必要な試験は、[`TEST_PLAN.md`](../TEST_PLAN.md) の「1.3 issue に書く試験条件」の表から選ぶ。最も狭いコマンドを先に、広いコマンドを後に書く。

## 3. ラベル

すべての開いている issue に、領域と優先度を 1 つ以上付ける。

| 種類 | ラベル | 意味 |
|---|---|---|
| 領域 | `area: core` | スケジュール計算、データモデル |
| | `area: ui` | Swing の画面、リボン |
| | `area: exchange` | MPO / MPP / POD / XML の読み書き |
| | `area: build` | Gradle、CI、リポジトリの衛生 |
| | `area: architecture` | 構造の分割、依存の方向 |
| | `area: msp-compat` | Microsoft Project との互換 |
| 優先度 | `priority: high` | 利用者の作業が止まる、データを失う、安全性に関わる |
| | `priority: medium` | 誤った結果や不便があるが、回避できる |
| | `priority: low` | 整理、将来のための改善 |
| 状態 | `status: ready` | 本文だけで着手できる。前提の作業が済んでいる |
| | `status: in progress` | 作業中。ブランチか PR がある |
| | `status: blocked` | 前提の issue か、所有者の判断を待っている。何を待っているかをコメントに書く |
| | `status: verification` | 修正は入った。元の報告の症状が消えたことの確認を待っている |
| 種別 | `bug` / `enhancement` / `documentation` | 不具合 / 改善 / 文書 |
| | `tracking` | 親 issue、索引 |
| | `good first issue` | 対象が 1〜3 ファイルで、設計の判断がない |

`status: ready` を付ける前に、次を確かめる。

- [ ] 本文に 5 つの見出しがそろっている
- [ ] 対象のファイルとシンボルが、今の master にある
- [ ] 検証のコマンドが、今の master で実行できる
- [ ] 前提の issue と PR が閉じている

## 4. 整理（トリアージ）

- 閉じてよいのは、完了条件をすべて満たしたとき、重複のとき、対象がなくなったときだけ。閉じるときは、理由と、根拠にした PR やコミットをコメントに書く。
- **修正の PR がマージされただけでは閉じない。** 元の報告の症状が消えたことを確認できていなければ、`status: verification` にして、閉じる条件をコメントに書く。
- 重複は、情報が多いほうを残す。閉じる側に、残した issue の番号を書く。対象が重なるだけで別の作業なら、両方に、進める順番を書く。
- 本文が短くて着手できない issue は、作業手順と完了条件をコメントで足す。報告者の本文は書き換えない。
- 親 issue のチェックリストは、子を閉じたときに更新する。
- 全体の索引は、ラベル `tracking` の索引 issue に 1 つだけ置く。新しい issue を作ったら、索引に足す。

## 5. ブランチ、コミット、PR

- master へ直接 push しない。master から作業ブランチを作り、PR で出す。必須チェックは `build` と `GUI acceptance`。
- 1 つの PR は 1 つの issue を扱う。PR の説明に `Closes #番号` を書く。一部だけを済ませた PR は `Refs #番号` と書き、残りを issue にコメントする。
- コミットの件名は「`領域: 変更の要約 (#番号)`」の形にする（例：`core: reject unsafe link schemes (#1036)`）。
- PR の説明には、実行した検証コマンドと結果を書く。実行していない確認を「通った」と書かない。
- コミット、PR、issue、コメントに、作業に使った道具やモデルの名前を書かない。
