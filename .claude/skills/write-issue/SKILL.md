# issue を書く、整理する

ルールの全文は `docs/issue-authoring.md` にある。ここには手順だけを書く。

## 書く前に確かめる

1. 同じ内容の issue がないかを探す：`gh issue list --state all --search "<キーワード>" --limit 20`。あれば、新しく作らずにコメントを足す。
2. 問題の場所を自分で確かめる。対象のファイルを開き、書こうとしているシンボルと動作が、今の master にあることを見る。人から聞いた行番号を、確かめずに書かない。
3. 設計の判断を済ませる。実装者に選ばせることが残っているなら、選ぶ基準を決めるか、先に調査の issue にする。
4. 1 つの PR で終わる大きさかを見る。大きければ、親（`tracking`）と子に分ける。

## 書く

テンプレート `.github/ISSUE_TEMPLATE/implementation-task.md` の見出しを使う（Microsoft Project との互換は `msp-compatibility.md`）。

- `## 概要`：何が問題で、誰が何に困るか。
- `## 作業手順`：番号付き。各手順に、パスとシンボル名、何をどう変えるか。
- `## 検証`：そのまま実行できるコマンド。`TEST_PLAN.md` の「1.3 issue に書く試験条件」から選ぶ。
- `## 完了条件`：チェックボックス。コマンドの結果かテストで判定できること。変えてはいけないものも入れる。
- `## 範囲外`：やらないことと、関連する issue の番号。

本文はファイルに書き、`gh issue create --title "<題名>" --body-file <ファイル> --label "<ラベル>"` で作る。シェルの引数に本文を直接渡さない（引用符と改行が壊れる）。

題名は、直したあとの状態か、する作業を 1 文で書く（例：「保存の前に一時ファイルをディスクへ書き出す」）。

## ラベルを付ける

領域（`area: *`）と優先度（`priority: *`）を必ず付ける。本文だけで着手できるなら `status: ready`。意味は `docs/issue-authoring.md` の「3. ラベル」。

## 作ったあと

- 索引の issue（ラベル `tracking`）に、新しい issue を足す。
- 事実と推測を分けて書いたかを読み直す。確かめていないことは、「未確認」と書く。
- 作業に使った道具やモデルの名前を、issue にもコメントにも書かない。
