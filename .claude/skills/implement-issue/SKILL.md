# issue を 1 件実装する

引数は issue の番号。issue の本文が仕様であり、本文にない設計の判断を自分で足さない。

## 1. 読む

1. `gh issue view <番号> --comments` で、本文と最新のコメントを読む。コメントが本文を上書きしていることがある。
2. 本文に「作業手順」「検証」「完了条件」がそろっていることを確かめる。そろっていない、または手順が今のコードと合わないときは、実装せずに、足りない点を issue にコメントして止まる。
3. ラベルが `status: blocked` のとき、または前提の issue が開いているときは、着手しない。

## 2. 準備する

1. `git status` で、自分のものではない変更がないことを確かめる。あれば触らない。
2. `git fetch origin master` のあと、`origin/master` から作業ブランチを作る。名前は `issue-<番号>-<短い英語の説明>`。本文に「骨格」のブランチが書かれていれば、そのブランチから続ける。
3. 対象のファイルを `rg` で探し、必要な範囲だけを読む。行番号がずれていたら、シンボル名で探す。

## 3. 実装する

- 作業手順の番号の順に進める。本文が「項目ごとにコミットを分ける」と言っていれば、そのとおりにする。
- `.editorconfig` に従う（UTF-8、CRLF、タブ）。新しいファイルには `Copyright (c) 2026 microProject` の MIT ヘッダーを付ける。パッケージは `com.microproject`。
- 「範囲外」に書かれたこと、関係のない整形やリネームはしない。
- 不具合の修正では、先に失敗するテストを書き、修正後に通ることを確かめる。
- 本文が決めていない選択が出てきたら、変更が小さく、元に戻しやすいほうを選び、理由を PR に書く。ファイル形式、スケジュール計算の結果、公開 API を変える選択は、自分で決めずに issue にコメントして止まる。

## 4. 検証する

1. 本文の「検証」のコマンドを、書かれた順に実行する。出力はファイルに保存し、失敗と要約だけを読む。
   ```
   .\gradlew.bat <タスク> --console=plain > "$env:TEMP\verify.log" 2>&1; $LASTEXITCODE
   ```
2. `git diff --check` が空であることを確かめる。
3. 完了条件を 1 行ずつ確かめ、満たした根拠（コマンドと結果、テスト名）を控える。
4. 同じ失敗を 2 回直しても通らないときは、3 回目を試す前に、原因を調べ直す。分からなければ、分かったことを issue にコメントして止まる。試験を無効にしたり、期待値を弱めたりして通さない。

## 5. 出す

1. コミットの件名は「`領域: 変更の要約 (#番号)`」。作業に使った道具やモデルの名前を、コミットにも PR にも書かない。
2. `git push -u origin <ブランチ>` のあと、`.github/pull_request_template.md` の見出しに沿って PR を作る。説明に `Closes #<番号>`（一部だけなら `Refs #<番号>`）と、実行したコマンドと結果を書く。
3. 実行していない確認、満たせなかった完了条件は、PR の「残っている作業」に書く。「通った」と書いてよいのは、実行して通ったものだけ。
4. マージはしない。必須チェック（`build`、`GUI acceptance`）の結果を待ち、失敗したら原因を調べて直す。
